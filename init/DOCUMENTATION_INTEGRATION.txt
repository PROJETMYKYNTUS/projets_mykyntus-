Intégration microservice Documentation — périmètre stable (docker-compose + init uniquement)
============================================================================================

0) Exécution uniquement via Docker (pas de ng serve / dotnet run sur la machine hôte)
   - À la racine du dépôt : docker compose build --parallel 1   puis   docker compose up -d
   - Après un git clone : aucune étape manuelle (pas de .env). Les bases sont créées par init.sql ; AuthService et le job auth-atlas-doc-users-seed remplissent auth_db ; documentation-backend crée le schéma (EnsureCreated) puis insère l’annuaire démo atlas-tech-demo si Documentation__DemoDataSeed=true (docker-compose) ; planning-backend et formation-backend insèrent des données de démo lorsque KYNTUS_PLANNING_DEMO_SEED / KYNTUS_FORMATION_DEMO_SEED sont à true. Pour repartir de zéro sur Postgres : docker compose down -v puis docker compose up -d.
   - Gateway API : http://localhost:8500
   - Identité documentation : JWT + middleware backend (`Documentation__AllowHeaderContextFallback`) ; le frontend peut poser X-Tenant-Id / X-User-* (interceptors SPA). Ne pas figer des UUID démo dans Ocelot en production.
   - Schéma PostgreSQL : init.sql crée la base documentation_db, l’utilisateur documentation_user, le schéma **documentation** et les droits (EF : HasDefaultSchema("documentation")). Le backend démarre avec Documentation__ApplyBootstrapSchema=true pour EnsureCreated (tables). Erreur 42P01 = tables absentes ; erreur **42501 permission denied for schema documentation** = droits Postgres : voir §6 (réparation sur volume existant).
   - Planning UI (SPA unifiée) : http://localhost:8200 (documentation : http://localhost:8200/documentation — /api/ et /hubs/ via nginx → api-gateway)
   - Auth UI : http://localhost:8201
   - Pas besoin d’ouvrir les ports backends (8520–8565) pour le navigateur : tout métier passe par la gateway ou le proxy nginx des frontends. Diagnostic documentation direct : http://localhost:8530
   - Postgres depuis la machine hôte : localhost:8433 (utilisateur postgres, mot de passe du docker-compose). pgAdmin web : http://localhost:8505 — ce n’est pas l’URL des appels HTTP de l’app documentation (ceux-ci passent par :8500 ou /api).

1) Point d’entrée API / SignalR (obligatoire pour le navigateur et les SPA)
   - Hôte : http://localhost:8500  →  conteneur api-gateway (Ocelot).
   - Préfixes REST documentation : /api/documentation , /api/generate-document-ai
   - Hub SignalR documentation : /hubs/documentation (négociation : /hubs/documentation/negotiate) — routes déclarées **avant** le catch-all `/hubs/{everything}` dans ocelot.gateway.json.
   - Définition des routes : init/ocelot.gateway.json (downstream : documentation-backend:8080).

2) Frontends (même convention que le planning)
   - Une seule SPA planning-frontend (port hôte 8200) : nginx envoie /api/ et /hubs/ vers api-gateway:8080 ; la documentation est une route lazy `/documentation` dans cette même app.
   - Aucun appel métier documentation ne doit viser directement le port public 8530 depuis une autre appli en production ; ce port sert au diagnostic local du backend.

3) Passage planning → documentation (sans jeton) — boutons existants, HTTP via api-gateway
   - Tous les appels REST documentation du front passent par `/api/...` (nginx planning-frontend → api-gateway), jamais en direct sur le port du DocumentationBackend.
   - RH / Admin (dashboard principal) : entrée « Documentation RH » → `/documentation/hr-mgmt` avec `?handoff=rh&email=…` (interface gestion RH).
   - Employé / pilote (dashboard employé) : entrée « Documentation » → `/documentation` avec `?handoff=pilote&email=…` (interface pilote / collaborateur).
   - Paramètres supportés : ?handoff=rh&email=… et ?handoff=pilote&email=…
   - La zone documentation résout l’utilisateur dans l’annuaire (GET …/data/users), applique le profil (en-têtes X-* côté gateway / démo) puis affiche l’écran attendu.

4) Erreurs à ne pas reproduire (rappel architecture)
   - Ne pas faire transiter un JWT ou secret entre applications via query string ou URL.
   - Ne pas coupler deux microservices backends entre eux hors contrats prévus ; le trafic UI passe par la gateway.
   - Les en-têtes métier documentation (tenant, rôle, utilisateur) sont posés par la chaîne d’auth / gateway selon les conventions du dépôt, pas par duplication ad hoc entre services.

5) Rôles / accès (logique fonctionnelle côté front)
   - Analyse de référence uniquement : projet_kyntus_service_planning-frontend_backup
   - RH / Admin : entrée vers l’espace gestion documentation (équivalent gestion des demandes).
   - Employé / pilote : entrée vers l’espace documentation collaborateur (mes demandes / demande de document).
   - Les conditions exactes (JWT, rôles) restent celles du frontend planning stable ; ce fichier ne duplique pas le code.

6) Base de données
   - Création utilisateur / base documentation + schéma **documentation** + GRANT : init.sql à la racine du dépôt (hors dossier init/).
   - Seed optionnel auth pour démo doc : init/sql/auth_insert_atlas_doc_users.sql (service compose auth-atlas-doc-users-seed).
   - Volume Postgres **déjà** initialisé (ancien init.sql sans schéma documentation) : le front peut appeler l’API mais le backend renvoie 500 avec **42501 permission denied for schema documentation**. Corriger sans tout perdre :
       docker compose exec -T postgres psql -U postgres -d documentation_db -f /tmp/repair.sql
     en copiant au préalable init/sql/repair_documentation_schema_permissions.sql dans le conteneur, ou depuis le dépôt (PowerShell, racine du repo) :
       Get-Content .\init\sql\repair_documentation_schema_permissions.sql -Raw | docker compose exec -T postgres psql -U postgres -d documentation_db
     Puis redémarrer documentation-backend : docker compose restart documentation-backend
   - Réinit complète (efface toutes les bases du volume) : docker compose down -v puis docker compose up -d (init.sql rejoué).
